# Game Sheet Exporter — 기획서

> **초안 — 검토 전입니다.**
> 승인 전에는 이 문서를 근거로 파서·검증·에미터 구현을 시작하지 마십시오.
> 실제 데이터시트가 없는 상태에서 작성했으므로, 시트 관습과 충돌하는 부분이 나오면
> 코드가 아니라 이 문서를 먼저 고칩니다.
>
> 검토가 필요한 판단은 [§11 결정이 필요한 지점](#11-결정이-필요한-지점)에 모아두었습니다.

타입 표기 문법은 [notation.md](./notation.md)에 분리했습니다.

## 1. 배경과 목적

게임 데이터는 엑셀에서 만들어지고 게임은 C#으로 돌아갑니다. 그 사이를 잇는 일은
대개 프로젝트마다 새로 짠 스크립트가 맡고, 그 스크립트는 대체로 이렇게 실패합니다.

- **타입이 없다** — 셀 값을 보고 짐작한다. 빈 셀이 `0`이 되어 밸런스가 조용히 틀어진다.
- **오류가 늦게 드러난다** — 잘못된 참조 ID가 빌드까지 통과하고 런타임에 `NullReference`로 나타난다.
- **어디가 틀렸는지 안 알려준다** — "파싱 실패"만 뜨고 어느 셀인지는 사람이 찾는다.
- **출력이 흔들린다** — 같은 시트를 두 번 내보내면 diff가 생겨 코드 리뷰가 무의미해진다.

이 도구는 네 가지를 각각 정면으로 다룹니다.

| 문제 | 해법 |
|---|---|
| 타입 없음 | 시트 안에 타입 행을 두고 표기법으로 명시 ([notation.md](./notation.md)) |
| 늦은 오류 | 내보내기 전에 참조 무결성·enum·형식을 전부 검증 (§5) |
| 위치 불명 | 모든 검증 결과에 `Monster!D17` 좌표를 붙인다 (§5.1) |
| 흔들리는 출력 | 같은 입력 → 바이트 단위로 같은 출력 (§8) |

### 1.1 왜 브라우저 도구인가

데이터 담당자가 파이썬 환경을 세팅하거나 CLI를 배우지 않아도 됩니다. 파일을 끌어다
놓으면 끝이고, 파일은 브라우저 밖으로 나가지 않습니다. 미공개 게임 데이터를
외부 서비스에 올리는 문제도 없습니다.

설치가 필요 없다는 것은 **버전 불일치가 없다**는 뜻이기도 합니다. 팀원마다 다른
버전의 변환 스크립트를 돌려 다른 결과가 나오는 상황이 생기지 않습니다.

### 1.2 사용자

| 사용자 | 하는 일 | 필요한 것 |
|---|---|---|
| 기획·밸런스 담당 | 시트를 쓰고 오류를 고친다 | 어느 셀이 왜 틀렸는지 |
| 클라이언트 프로그래머 | 생성된 C#을 프로젝트에 넣는다 | 컴파일되는 코드, 안정된 diff |
| 빌드 담당 | 데이터 갱신을 파이프라인에 태운다 | 결정적 출력, 향후 CLI 전환 |

마지막 항목 때문에 `src/core/`가 브라우저 API를 쓰지 않습니다. CLI로 옮길 때
진입점 파일 하나만 새로 쓰면 되도록 하는 것이 이 제약의 목적입니다.

## 3. 입력 — 시트 포맷 규약

이 절이 데이터 담당자가 지켜야 할 규약입니다.

### 3.1 헤더 구성

```
      A          B            C      D             E
1  │ id        │ name       │ hp   │ grade       │ drop_ids       ← 필드명
2  │ int       │ loc        │ int  │ enum:Grade  │ ref:Item.id[]  ← 타입
3  │ 고유ID     │ 이름        │ 체력  │ 등급         │ 드랍            ← 주석
4  │ 1001      │ MON_SLIME  │ 30   │ Normal      │ 2001,2002      ← 데이터
```

| 행 | 내용 | 비고 |
|---|---|---|
| 1 | 필드명 | JSON 키와 C# 필드명의 원본 (§6.4) |
| 2 | 타입 표기 | [notation.md](./notation.md) |
| 3 | 주석 | 사람용. 출력에는 XML 문서 주석으로만 들어간다 |
| 4~ | 데이터 | |

**행 번호는 설정값입니다.** 1·2·3행으로 하드코딩하지 않습니다. 기존 시트를 가진
팀이 헤더를 옮기지 않고 이 도구를 쓸 수 있어야 합니다. 주석 행은 없앨 수도 있습니다.

한 워크북 안에서는 모든 시트가 같은 헤더 구성을 씁니다. 시트마다 다르면 설정 하나로
파싱할 수 없습니다.

### 3.2 시트와 열의 종류

| 대상 | 규칙 |
|---|---|
| 데이터 시트 | 기본 |
| enum 정의 시트 | 시트명이 `enum.` 으로 시작 (§3.3) |
| 무시 시트 | 시트명이 `#` 또는 `_` 로 시작 |
| 무시 열 | 필드명이 비었거나 `#` 로 시작 |

무시 규칙이 필요한 이유는 실제 시트에 계산용 임시 열과 메모 시트가 늘 섞여 있기 때문입니다.
그걸 지우라고 요구하는 도구는 쓰이지 않습니다.

### 3.3 enum 정의 시트

시트명 `enum.Grade` → C# `enum Grade`

```
      A          B        C
1  │ name      │ value  │ comment
2  │ string    │ int?   │ string?
3  │ 이름       │ 값      │ 설명
4  │ Normal    │ 0      │ 일반
5  │ Rare      │ 10     │ 희귀
6  │ Unique    │        │ 유니크        ← value 생략 시 이전 값 + 1
```

- `name` 필수, C# 식별자로 쓸 수 있어야 한다
- `value` 생략 가능. 생략하면 이전 멤버 + 1, 첫 멤버면 0
- 이름 중복·값 중복은 `E010`
- 열은 **필드명으로 찾습니다.** 순서는 자유입니다
- **타입 행은 읽지 않습니다.** 이 시트의 스키마는 도구가 정하는 것이라 사용자가 바꿀
  수 없습니다. 위 예시의 타입 행은 사람이 읽는 설명이고, 파서는 무시합니다

값을 명시할 수 있게 두는 이유는 저장된 세이브 데이터와의 호환 때문입니다. 멤버를
중간에 추가했을 때 뒤쪽 값이 밀리면 이미 저장된 데이터가 다른 의미가 됩니다.

### 3.4 기본키

각 시트의 **첫 번째 필드가 기본키**입니다.

- 값이 유일해야 한다 (`E012`)
- 빈 값일 수 없다 (`E003`)
- 생성된 로더의 조회 인덱스가 된다 (§6.3)

`ref:Sheet.Field`의 대상이 기본키가 아닌 다른 필드여도 됩니다. 그 경우 그 필드에도
유일성 검증이 걸립니다.

### 3.5 CSV 입력

시트가 하나뿐인 워크북으로 취급합니다. 시트명은 파일명에서 가져옵니다.
인코딩은 UTF-8만 받습니다 (BOM 유무는 무관). CP949 시트는 변환 후 넣습니다 —
인코딩 자동 판별은 틀렸을 때 조용히 깨지므로 하지 않습니다.

## 4. 중간 표현 (IR)

파서의 출력이자 검증기·에미터의 입력입니다. 모든 하위 모듈은 IR만 보고 동작하며
SheetJS도 DOM도 모릅니다.

```jsonc
{
  "irVersion": 1,
  "source": { "fileName": "gamedata.xlsx", "sheetCount": 3 },
  "layout": { "nameRow": 1, "typeRow": 2, "commentRow": 3, "dataStartRow": 4 },

  "enums": [
    {
      "name": "Grade",
      "sheet": "enum.Grade",
      "members": [
        { "name": "Normal", "value": 0, "comment": "일반", "cell": "enum.Grade!A4" }
      ]
    }
  ],

  "sheets": [
    {
      "name": "Monster",              // 원본 시트명
      "className": "Monster",         // naming.js 변환 결과
      "primaryKey": "id",
      "fields": [
        {
          "name": "id",               // 원본 필드명
          "identifier": "id",         // naming.js 변환 결과 = JSON 키 = C# 필드명
          "column": 0,
          "columnLetter": "A",
          "type": { "kind": "scalar", "name": "int" },
          "comment": "고유ID",
          "cell": "Monster!A1"
        }
      ],
      "rows": [
        {
          "row": 4,
          "values": { "id": 1001, "drop_ids": [2001, 2002] },
          "cells":  { "id": "Monster!A4", "drop_ids": "Monster!E4" }
        }
      ]
    }
  ]
}
```

### 4.1 설계 근거

- **`irVersion`** — 골든 파일이 IR을 비교하므로 구조가 바뀌면 명시적으로 올린다.
- **`cells`를 값과 나란히 둔다** — 검증기가 오류를 낼 때 좌표를 역산하지 않아도 된다.
  좌표 계산이 검증 규칙마다 흩어지면 `Monster!D17`이 어긋나기 시작한다.
- **`name`과 `identifier`를 함께 보관** — 리포트는 사람이 시트에서 찾을 수 있게 원본
  이름을 쓰고, 출력은 변환된 식별자를 쓴다. 하나만 들고 있으면 둘 중 하나가 깨진다.
- **`values`는 캐스팅 완료 상태** — 에미터는 문자열을 다시 해석하지 않는다.

## 5. 검증

이 도구의 존재 이유입니다. 검증이 부실하면 나머지가 아무리 좋아도 신뢰를 얻지 못합니다.

### 5.1 리포트 형식

```
E004  Monster!E4  참조 대상이 없습니다: Item.id = 2003
                  drop_ids 열의 값 2003 이 Item 시트에 없습니다.
W105  Monster!B1  필드명이 변환되었습니다: "몬스터 이름" → "몬스터_이름"
```

**좌표 없는 검증 결과는 미완성으로 간주합니다.** 시트 전체에 걸린 오류는 `Monster!` 까지,
파일 전체면 파일명까지 표기합니다.

`E` 하나라도 있으면 내보내기를 막습니다. `W`는 진행하되 리포트에 남깁니다.

### 5.2 오류 (E) — 내보내기 중단

| 코드 | 이름 | 조건 |
|---|---|---|
| `E001` | 필드명 오류 | 같은 시트에 중복된 필드명. 타입은 있는데 필드명이 빔 |
| `E002` | 타입 표기 누락 | 필드명은 있는데 타입 셀이 빔 |
| `E003` | 필수 값 누락 | nullable 아닌 필드의 셀이 빔 ([notation §5.2](./notation.md#52-빈-셀)) |
| `E004` | 참조 대상 값 없음 | `ref:` 의 값이 대상 시트에 존재하지 않음 |
| `E005` | 타입 표기 파싱 실패 | [notation §7](./notation.md#7-거부-사례) |
| `E006` | 값 캐스팅 실패 | `int` 열에 `abc`, `bool` 열에 `maybe`, 배열의 빈 원소 등 |
| `E007` | C# 예약어 충돌 | 변환된 식별자가 예약어 (§6.4) |
| `E008` | 참조 대상 정의 없음 | `ref:` 의 시트·필드, `enum:` 의 정의 시트가 없음 |
| `E009` | enum 멤버 없음 | 값이 enum 정의에 없음 |
| `E010` | enum 정의 오류 | 멤버 이름 중복, 값 중복, 이름 누락 |
| `E011` | 식별자 변환 불가 | 변환 결과가 빈 문자열 (필드명이 `!!!` 같은 경우) |
| `E012` | 유일성 위반 | 기본키 또는 참조 대상 필드에 중복 값 |
| `E013` | 지원하지 않는 타입 | 배열 깊이 2 이상 등 ([notation §2.2](./notation.md#22-중첩-제한)) |
| `E014` | 로컬라이즈 키 없음 | `loc` 값이 키 테이블에 없음 (테이블을 넣은 경우에만) |
| `E015` | 클래스명 충돌 | 서로 다른 시트가 같은 C# 클래스명으로 변환됨 |

### 5.3 경고 (W) — 진행하되 리포트

| 코드 | 이름 | 조건 |
|---|---|---|
| `W101` | 미사용 enum 멤버 | 어느 시트에서도 쓰이지 않음. 오타로 만든 멤버를 잡는다 |
| `W102` | 데이터 행 없음 | 헤더만 있고 데이터가 없는 시트 |
| `W103` | 빈 열 | 모든 데이터 행에서 비어 있는 열 |
| `W104` | 주석 없음 | 주석 행이 비어 있음. 생성 코드에 문서 주석이 안 붙는다 |
| `W105` | 식별자 변환됨 | 원본 이름과 변환 결과가 다름 (§6.4) |
| `W106` | 로컬라이즈 키 형식 | `loc` 값이 `[A-Z][A-Z0-9_]*` 형식이 아님 |

### 5.4 규칙 하나당 파일 하나

`src/core/validate/rules/E001.js` 형태로 규칙마다 파일을 나눕니다. 규칙이 20개를
넘어가면 한 파일에 모아둔 검증기는 읽을 수 없게 됩니다.

각 규칙은 **최소 한 개의 실패 케이스와 한 개의 통과 케이스**를 테스트로 갖습니다.

규칙은 `validator.js`의 배열에 **명시적으로 등록**합니다. 디렉터리를 훑지 않는 이유가
둘 있습니다 — `core/`는 브라우저에서 그대로 돌아야 해 파일 시스템을 못 쓰고, 번들러가
없으므로 동적 임포트의 경로를 정적으로 알 수 없습니다. 부수 효과로 실행 순서가 소스에
박혀 결정성(§8)이 따라옵니다. 파일만 만들고 등록을 잊으면 규칙이 조용히 실행되지
않으므로, 등록 개수를 테스트가 확인합니다.

### 5.5 파싱 단계 진단과 검증 단계 진단

모든 코드가 규칙 파일이 되는 것은 아닙니다. 기준은 **"IR에 넣을 값을 정할 수 있는가"**
하나입니다.

| 단계 | 코드 | 위치 |
|---|---|---|
| 파싱 중 | `E001` `E002` `E003` `E005` `E006` `E008` `E010` `E013` | `core/parser/` 가 직접 낸다 |
| IR 완성 후 | `E004` `E007` `E009` `E011` `E012` `E014` `E015` · `W101`~`W106` | `core/validate/rules/` |

§4.1이 "`values`는 캐스팅 완료 상태"를 요구하므로 캐스팅은 파서에 있습니다. 그러면
빈 `int` 셀을 만난 시점에 이미 `E003`인 것을 알게 되고, 이를 검증 단계로 미루려면
타입 트리를 한 번 더 걸어야 합니다. 같은 판단을 두 곳에서 하면 두 곳이 갈라집니다.

`E008`(참조 대상 정의 없음)이 파싱 단계인 이유는 `ref:Item.id`의 값을 캐스팅하려면
`Item.id`의 타입을 먼저 알아야 하기 때문입니다. 대상이 없으면 캐스팅 자체를 못 합니다.

두 단계는 **같은 진단 객체**(`{ code, cell, message, detail }`)를 냅니다. 사용자는
어느 단계에서 나왔는지 알 필요가 없고, 리포트는 §5.1 형식 하나입니다.

## 6. 출력

### 6.1 JSON

시트당 파일 하나입니다.

`Monster.json`
```json
{
  "rows": [
    {
      "id": 1001,
      "name": "MON_SLIME",
      "hp": 30,
      "grade": "Normal",
      "drop_ids": [2001, 2002]
    }
  ]
}
```

- **키 순서 = 시트 열 순서.** 알파벳 정렬하지 않는다
- 최상위를 `{ "rows": [...] }` 로 감싼다 — 나중에 메타데이터를 붙일 자리를 남겨둔다
- 들여쓰기 2칸, 줄바꿈 LF, 파일 끝 개행 있음
- `datetime` 은 UTC ISO 8601 문자열
- `enum` 은 멤버 이름 문자열
- 압축 출력은 옵션 (`minify`)

### 6.2 CSV

시트당 파일 하나. 헤더 한 줄(변환된 필드명) + 데이터 행.
배열은 셀 안에서 `,` 로 이어 붙이고 필드 전체를 큰따옴표로 감쌉니다.
줄바꿈 LF, UTF-8 BOM 없음.

CSV는 차이 확인과 다른 도구 연동용입니다. 게임 런타임이 읽는 형식은 JSON입니다.

### 6.3 C#

세 종류를 냅니다.

**`Grade.cs`** — enum
```csharp
namespace GameData
{
    /// <summary>등급</summary>
    public enum Grade
    {
        /// <summary>일반</summary>
        Normal = 0,
        /// <summary>희귀</summary>
        Rare = 10,
    }
}
```

**`Monster.cs`** — 데이터 클래스
```csharp
using System;
using System.Collections.Generic;

namespace GameData
{
    /// <summary>Monster 시트의 한 행입니다.</summary>
    [Serializable]
    public sealed class Monster
    {
        /// <summary>고유ID</summary>
        public int id;

        /// <summary>이름 (로컬라이즈 키)</summary>
        public string name;

        /// <summary>체력</summary>
        public int hp;

        /// <summary>등급</summary>
        public Grade grade;

        /// <summary>드랍 (→ Item.id)</summary>
        public List<int> drop_ids;
    }
}
```

**`GameDataTables.cs`** — 로더
```csharp
namespace GameData
{
    public sealed class GameDataTables
    {
        public IReadOnlyList<Monster> Monsters { get; }
        public IReadOnlyList<Item> Items { get; }

        public Monster GetMonster(int id);
        public bool TryGetMonster(int id, out Monster value);

        /// <param name="readJson">테이블 이름을 받아 JSON 문자열을 돌려준다.</param>
        public static GameDataTables Load(Func<string, string> readJson);
    }
}
```

`Load`가 파일 읽기를 직접 하지 않고 함수를 받는 이유는, Resources·Addressables·
StreamingAssets·테스트용 문자열 중 무엇을 쓸지는 프로젝트가 정할 일이기 때문입니다.
`src/core/`가 `ports.js`로 외부 기능을 주입받는 것과 같은 발상입니다.

조회 인덱스(`GetMonster`)는 기본키(§3.4) 기준으로 생성자에서 한 번 만듭니다.

**옵션**: 네임스페이스, 파일 분리 여부, 접근 제한자, 필드 대신 프로퍼티 사용,
헤더 주석의 타임스탬프 포함 여부.

### 6.4 식별자 변환 — `naming.js`

시트명·필드명에는 공백, 한글, 특수문자가 들어옵니다. 변환은 **이 파일 하나만** 합니다.
두 곳에서 변환하면 JSON 키와 C# 필드명이 조용히 어긋나고, 증상은 "런타임에 필드가
전부 기본값"으로 나타나 원인을 찾기 어렵습니다.

**필드명 — 최소 변환**

1. 유니코드 NFC 정규화
2. C# 식별자로 쓸 수 없는 문자를 `_` 로 치환
3. 숫자로 시작하면 `_` 를 앞에 붙임
4. 결과가 빈 문자열이면 `E011`
5. C# 예약어면 `E007` — **자동으로 이름을 바꾸지 않는다**
6. 원본과 다르면 `W105`

대소문자는 건드리지 않습니다. `drop_ids` 를 `DropIds` 로 바꾸면 시트를 쓴 사람이
생성 코드에서 자기 열을 못 찾습니다.

한글 필드명은 **그대로 둡니다**. C# 명세상 유니코드 식별자는 합법이고 Unity에서도
컴파일됩니다. 로마자로 옮기는 것은 원본과의 연결을 끊는 일이라 하지 않습니다.

**시트명 — PascalCase 변환**

클래스명은 C# 관습을 따릅니다. 공백·하이픈·점·밑줄을 단어 경계로 보고 PascalCase로
만듭니다. `몬스터 정보` → `몬스터정보`, `item-drop` → `ItemDrop`.

변환 결과가 겹치면 `E015`입니다.

**예약어 목록**은 C# 키워드 전체와 문맥 키워드(`value`, `var`, `record` 등)를 포함합니다.
`class`, `event`, `params`, `object`, `string`, `int` 가 실제 시트에서 자주 부딪힙니다.

## 8. 결정성

**같은 입력은 바이트 단위로 같은 출력을 냅니다.** 생성 코드를 저장소에 커밋하는
이상, 이게 깨지면 데이터를 안 바꿔도 diff가 생기고 코드 리뷰가 무의미해집니다.

| 요건 | 확인 방법 |
|---|---|
| 키 순서 = 시트 열 순서 | 골든 파일 |
| 줄바꿈 LF 고정 | `.gitattributes` + 골든 파일 |
| 출력 경로에서 현재 시각을 읽지 않음 | 타임스탬프 제외 옵션으로 날짜 부재 확인 |
| `Set`/`Map` 순회, `Object.keys` 순서에 의존하지 않음 | 2회 실행 결과 바이트 비교 |

헤더 타임스탬프가 필요하면 **옵션으로 주입**합니다. 코드가 직접 `Date.now()` 를
부르지 않습니다.

## 11. 결정이 필요한 지점

초안을 쓰면서 제가 판단한 것들입니다. 실제 시트가 없어 근거가 약한 순서로 적었습니다.

### 11.1 Unity JSON 역직렬화 — Newtonsoft 전제 ✅ 확정 (2026-07-29)

Unity 기본 `JsonUtility` 는 제약이 많습니다.

| 제약 | 이 기획서에 미치는 영향 |
|---|---|
| `Nullable<T>` 미지원 | `int?` 표기를 쓸 수 없다 |
| 최상위 배열 미지원 | 래퍼 필요 (그래서 §6.1이 `{"rows":[...]}`) |
| `DateTime` 미지원 | `datetime` 을 문자열로 두고 변환 프로퍼티가 필요 |
| enum을 정수로만 처리 | JSON에서 `"Normal"` 대신 `0` 이 되어 사람이 못 읽는다 |
| `Dictionary` 미지원 | 향후 `map:` 표기 확장이 막힌다 |

이 초안은 **`com.unity.nuget.newtonsoft-json` 사용을 전제**했습니다. Unity가 공식
패키지로 제공하고 `manifest.json` 한 줄이면 되며, 이걸 전제하면 위 제약이 전부
사라져 타입 체계를 깔끔하게 유지할 수 있습니다.

전제하지 않는다면 `?` 표기를 없애고 enum을 정수로 내보내는 등 타입 체계를 줄여야
합니다.

**결정: Newtonsoft 를 전제합니다.** 따라서 §6 은 초안 그대로 확정입니다.

| 항목 | 확정된 출력 |
|---|---|
| enum | 멤버 **이름 문자열** (`"Normal"`). 정수가 아니다 |
| 빈 값 | `null`. 키를 빼지 않는다 |
| `datetime` | UTC ISO 8601 문자열 |
| 최상위 | `{ "rows": [...] }` |

이 결정을 뒤집으면 `notation.md` §2 의 `?` 표기부터 되돌려야 하므로, 바꾸려면
S1·S2 구현까지 함께 봅니다. Unity 쪽 준비는 `manifest.json` 에
`com.unity.nuget.newtonsoft-json` 한 줄입니다.

### 11.2 그 밖의 판단

| 판단 | 대안 | 근거 |
|---|---|---|
| 첫 번째 필드 = 기본키 | `id` 라는 이름으로 고정 / 명시 표기 추가 | 규약이 단순하고 예외가 없다 |
| enum을 전용 시트로 정의 | 사용된 값에서 자동 수집 | 오타가 새 멤버가 되는 것을 막는다 |
| 빈 셀은 기본값 없이 오류 | `int` → `0` 자동 | 조용한 `0` 이 가장 찾기 어려운 버그다 |
| 필드명 대소문자 유지 | PascalCase 변환 | 시트를 쓴 사람이 생성 코드에서 자기 열을 찾을 수 있어야 한다 |
| 한글 식별자 허용 | 로마자 변환 / 거부 | C# 명세상 합법. 변환은 원본과의 연결을 끊는다 |
| 배열 구분자 `,` | `;` 또는 `\|` | 가장 흔하다. 설정으로 바꿀 수 있게 둔다 |
| 엑셀 시리얼 60 이하 거부 | 1900 윤년 버그 보정 | 조용히 하루 어긋나는 것보다 낫다 |
| CSV 인코딩 UTF-8 한정 | 자동 판별 | 판별 실패가 조용한 깨짐으로 나타난다 |
| `int??` 를 오류로 | `int?` 와 동일 취급 | 같은 타입의 표기가 둘로 갈리는 것을 막는다 |
| `long` 안전 정수 범위 밖 거부 | BigInt 보관 / 문자열 보관 | 조용한 반올림보다 낫다 ([notation §3.3](./notation.md#33-long-의-정밀도)) |

### 11.3 실제 시트가 나오면 다시 볼 것

- 헤더 행 구성 기본값 (3행이 맞는지)
- 배열 구분자
- `bool` 허용 표기 (`O`/`X` 를 실제로 쓰는지)
- 무시 열·무시 시트 접두 규칙 (`#`, `_` 가 실제 관습과 맞는지)
- 자주 등장하는 열 이름과 C# 예약어 충돌 빈도
