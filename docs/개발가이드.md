# Sheet Exporter — Claude Code 개발 가이드

> 대상 저장소: `blackrabbitDeveloper/sheet-exporter` (신규)
> 기반: `blackrabbit-ui` v0.3.0 (zero-build, MIT)
> 사양: [Excel DataTable Exporter 기획서](./excel-datatable-exporter-기획서.md)

---

## 0. 이 문서의 전제

Claude Code는 **컨텍스트가 좁을수록 정확**합니다. "이 기획서대로 만들어줘"라고 한 번에 던지면 초반 몇 파일은 그럴듯하게 나오지만, 중반부터 기존 모듈을 무시하고 중복 구현을 쌓기 시작합니다. 이 가이드는 그걸 막기 위해 **작업을 세션 단위로 쪼개고, 각 세션의 성공 조건을 테스트로 못 박는** 방식으로 구성되어 있습니다.

핵심 원칙 세 가지:

1. **경계를 코드로 강제한다** — `src/core/`는 브라우저 API를 못 쓰게 하고, 그 결과 Node에서 그대로 테스트된다. 테스트가 돌면 경계가 지켜진 것이다.
2. **성공 조건은 항상 실행 가능한 명령이다** — "잘 동작하면 됨"이 아니라 `npm test` 통과.
3. **CLAUDE.md는 짧게 유지한다** — Claude Code는 <cite index="13-1">CLAUDE.md를 강제 설정이 아니라 컨텍스트로 취급하며, 지시가 구체적이고 간결할수록 일관되게 따릅니다. 200줄이 넘으면 컨텍스트 소모가 커집니다.</cite>

## 1. 저장소 설계

### 1.1 왜 별도 저장소인가

blackrabbit-ui의 sync 스크립트가 형제 저장소에 배포본을 복사하는 구조이므로, 기존 앱들(`convert-to-image`, `mdviewer` 등)과 동일하게 독립 저장소로 둡니다.

```
~/work/
  blackrabbit-ui/        ← 디자인 시스템 (원본)
  convert-to-image/
  mdviewer/
  sheet-exporter/        ← 이번에 만들 것
```

### 1.2 스캐폴딩

`blackrabbit-ui` 디렉터리에서 실행합니다.

```bash
cd ~/work/blackrabbit-ui
npm run build
npm run create -- ../sheet-exporter \
  --template=utility \
  --name="Sheet Exporter" \
  --command="sheet.export" \
  --description="엑셀 데이터시트를 타입이 보존된 JSON과 C# 코드로 내보냅니다." \
  --accept=".xlsx,.xlsm,.csv" \
  --accept-label="XLSX · XLSM · CSV"
```

utility 템플릿의 **파일 입력 → 설정 → 처리 → 결과** 흐름이 이 툴과 정확히 일치하므로 셸을 거의 그대로 씁니다. Claude Code에게 UI를 처음부터 만들게 하지 마세요. 템플릿을 채우는 작업으로 지시해야 결과가 일관됩니다.

### 1.3 SheetJS 벤더링

zero-build 원칙상 번들러가 없으므로 npm 설치가 아니라 **파일을 직접 커밋**합니다.

```
vendor/
  blackrabbit-ui/
    blackrabbit-ui.css
    blackrabbit-ui.js
  sheetjs/
    xlsx.full.min.js       ← 브라우저/워커용
    xlsx.mjs               ← Node 테스트용 (또는 devDependency로만 설치)
    LICENSE                ← Apache-2.0 원문 동봉
```

> SheetJS는 npm 공개 배포를 중단하고 자체 CDN에서 배포합니다. 설치 경로를 먼저 확인하고, 받은 버전을 `vendor/sheetjs/VERSION` 파일에 기록해두세요. Claude Code가 `npm install xlsx`를 시도할 수 있으므로 CLAUDE.md에 명시적으로 금지 규칙을 넣습니다.

### 2.1 의존 방향 (단일 규칙)

```
ui  →  core        허용
worker → core      허용
core →  ui         금지
core →  브라우저 API  금지
core →  SheetJS    workbook-reader.js 에서만
```

이 규칙 하나가 Phase 2(CLI/CI 전환)의 전체 비용을 결정합니다. `core/`가 순수하면 CLI는 진입점 파일 하나만 새로 쓰면 됩니다.

### 2.2 해시 주입 예시

`core/`에서 `crypto`를 직접 쓰면 순수성이 깨집니다. 포트로 받으세요.

```js
// core/util/ports.js — 인터페이스 정의만
// { sha256: (Uint8Array) => Promise<string> }

// ui 쪽
const ports = { sha256: async (b) => bufToHex(await crypto.subtle.digest('SHA-256', b)) };

// test 쪽
import { createHash } from 'node:crypto';
const ports = { sha256: async (b) => createHash('sha256').update(b).digest('hex') };
```

## 3. CLAUDE.md 배치

저장소 루트에 두면 세션 시작 시 자동으로 로드됩니다. 별도 파일로 첨부했으니 그대로 복사하세요.

**중요한 성질 하나**: CLAUDE.md는 <cite index="13-1">강제 설정이 아니라 컨텍스트입니다. 무슨 일이 있어도 특정 동작을 차단하려면 PreToolUse 훅을 쓰라고 공식 문서가 안내합니다.</cite> 따라서 `vendor/` 수정 금지처럼 어겼을 때 피해가 큰 규칙은 훅으로 잠그는 편이 안전합니다.

```json
// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/guard-vendor.sh" }]
      }
    ]
  }
}
```

훅 스크립트는 대상 경로가 `vendor/`로 시작하면 비정상 종료시키면 됩니다. 처음부터 만들 필요는 없고, 한 번이라도 벤더 파일이 수정되는 사고가 나면 그때 추가하세요.

사양 문서는 CLAUDE.md 안에 복붙하지 말고 임포트로 참조합니다. <cite index="14-1">`@docs/spec.md` 형태의 상대 경로 임포트가 지원되며 최대 4단계까지 재귀됩니다.</cite>

## 4. 개발 순서 — 세션 분할

각 세션은 **하나의 관심사 + 통과하는 테스트 + 커밋 하나**로 끝냅니다. 세션이 끝나면 컨텍스트를 정리하고 다음 세션을 새로 시작하세요.

| # | 세션 | 산출물 | 성공 조건 |
|---|---|---|---|
| S0 | 골격 준비 | 스캐폴딩, CLAUDE.md, docs/spec.md, 픽스처 생성기 | `npm run fixtures` 로 xlsx 생성됨 |
| S1 | 타입 표기 파서 | `type-notation.js` | 표기법 전 항목 파싱/거부 테스트 통과 |
| S2 | 시트 → IR | `workbook-reader`, `header-parser`, `value-parser`, `build-ir` | basic 픽스처가 골든 IR과 일치 |
| S3 | 검증 코어 | `validator`, `report`, E001~E003 | broken 픽스처에서 정확한 좌표 리포트 |
| S4 | JSON/CSV 에미터 | `emit/json.js`, `emit/csv.js` | 골든 일치 + 2회 실행 바이트 동일 |
| S5 | C# 클래스·enum | `naming.js`, `enum.js`, `class.js` | 골든 `.cs` 일치 |
| S6 | C# 로더 | `loader.js` | 골든 일치, 실제 Unity 프로젝트에서 컴파일 확인(수동) |
| S7 | 참조 검증 | E004, E008 | refs 픽스처 통과 |
| S8 | UI 연결 | 템플릿 채우기, 시트 목록, 미리보기 탭 | 브라우저에서 xlsx 드롭 → JSON 표시 |
| S9 | 검증 패널 | `validation-panel.js`, 셀 하이라이트 | 오류 클릭 → 원본 셀로 이동 |
| S10 | 마감 | Worker 이관, 프리셋, ZIP | 10,000행 시트에서 UI 미차단 |
| S11 | 등재 | 사이트 목록 추가, README | `utils list` 에 노출 |

**순서가 이런 이유**: S1~S7은 전부 `core/`이고 DOM이 없어 Claude Code가 테스트로 자체 검증할 수 있습니다. 자체 검증이 가능한 구간을 먼저 끝내야 사람이 눈으로 확인할 일이 줄어듭니다. UI(S8~)는 사람이 봐야 하므로 뒤로 미룹니다.

### 4.1 세션 프롬프트 템플릿

```
docs/spec.md 의 4.3 타입 표기 스펙을 읽고 src/core/parser/type-notation.js 를 구현해줘.

입력: 타입 선언 문자열 하나
출력: TypeNode 객체. 종류는 scalar | nullable | array | enum | ref | loc | struct
파싱 불가 시 { code: 'E005', message } 를 담은 오류를 던진다.

제약:
- 이 파일은 다른 모듈을 import 하지 않는다. 순수 문자열 처리만.
- 정규식 한 방으로 처리하지 말고, 접미사(?, [])를 벗겨내며 재귀 하강으로 파싱해라. 중첩 표기가 나중에 추가된다.

먼저 test/type-notation.test.mjs 를 작성하고, 스펙 표의 모든 행 + 잘못된 입력 5종을 케이스로 넣어라.
그 다음 구현하고 npm test 가 통과할 때까지 반복해라.

작업 계획을 먼저 보여주고 승인을 받은 뒤 시작해라.
```

이 템플릿의 요소를 그대로 유지하세요: **입출력 계약 명시 → 제약 조건 → 테스트 먼저 → 검증 명령 → 계획 승인**. 특히 "정규식 한 방으로 처리하지 말라" 같은 **미래 확장을 아는 사람만 줄 수 있는 지시**가 결과 품질을 크게 바꿉니다.

## 5. 테스트 전략

### 5.1 픽스처는 생성한다

xlsx는 바이너리라 손으로 만들거나 Claude Code가 직접 편집할 수 없습니다. **JSON 정의를 원본으로 두고 스크립트로 xlsx를 생성**하세요.

```jsonc
// test/fixtures/basic.def.json
{
  "Monster": [
    ["id",   "name",      "hp",  "grade",      "drop_ids"],
    ["int",  "loc",       "int", "enum:Grade", "ref:Item.id[]"],
    ["고유ID", "이름",     "체력", "등급",       "드랍"],
    [1001,   "MON_SLIME", 30,    "Normal",     "2001,2002"]
  ],
  "Item": [
    ["id",  "name"],
    ["int", "loc"],
    [2001,  "ITEM_POTION"],
    [2002,  "ITEM_HERB"]
  ]
}
```

`npm run fixtures` → `test/fixtures/generated/*.xlsx`. 생성물은 gitignore하고 정의 파일만 커밋합니다. 이러면 Claude Code가 픽스처를 텍스트로 읽고 수정할 수 있습니다.

### 5.2 골든 파일

출력 형식이 있는 모든 것(IR, JSON, C#)은 골든 파일로 비교합니다.

```bash
npm test                    # 비교
UPDATE_GOLDEN=1 npm test    # 의도적 변경 시 갱신
```

골든 갱신은 **반드시 별도 커밋**으로 남기세요. 로직 변경과 골든 갱신이 한 커밋에 섞이면 diff에서 의도가 안 보입니다.

### 5.3 결정성 테스트

기획서에서 필수 요건으로 잡은 항목이므로 테스트로 고정합니다.

```js
test('동일 입력은 동일 바이트를 낸다', async () => {
  const a = emitCSharp(ir, opts);
  const b = emitCSharp(structuredClone(ir), opts);
  assert.strictEqual(a, b);
});

test('타임스탬프 제외 옵션이면 출력에 날짜가 없다', () => {
  const out = emitCSharp(ir, { ...opts, includeTimestamp: false });
  assert.ok(!/20\d{2}-\d{2}-\d{2}/.test(out));
});
```

`Object.keys` 순회 순서, `Set`/`Map` 삽입 순서 의존, `Date.now()` 혼입이 결정성을 깨는 3대 원인입니다. Claude Code가 무심코 넣기 쉬우니 CLAUDE.md에 명시해뒀습니다.

### 5.4 커버리지보다 중요한 것

E-코드 규칙은 **하나당 최소 한 개의 실패 케이스와 한 개의 통과 케이스**를 요구하세요. 검증기가 이 툴의 존재 이유이므로, 여기 테스트가 부실하면 나머지가 아무리 좋아도 신뢰를 못 얻습니다.

## 6. Claude Code 운용

### 6.1 계획 먼저

파일을 여러 개 건드리는 세션은 계획 모드로 시작해 접근을 확인한 뒤 실행하게 하세요. 특히 S2와 S8은 구조 결정이 걸려 있어 잘못된 방향으로 30분을 태우기 쉽습니다.

### 6.2 세션 경계 지키기

<cite index="15-1">Claude Code 세션은 매번 새 컨텍스트 창에서 시작합니다.</cite> 하나의 긴 세션에서 S1부터 S7까지 밀어붙이면 후반에 앞쪽 결정을 잊고 중복 구현이 생깁니다. 표의 한 행이 끝나면 커밋하고 세션을 끊으세요. 이어지는 맥락은 CLAUDE.md와 테스트 코드가 대신 전달합니다.

### 6.3 자체 검증 루프를 열어주기

`npm test` 실행 권한을 주면 Claude Code가 스스로 고칠 때까지 반복합니다. 이 루프가 있는 세션(S1~S7)과 없는 세션(S8~S10)의 결과 품질 차이가 큽니다. UI 세션에서는 **스크린샷을 붙여서 피드백**하는 방식으로 루프를 대신하세요.

### 6.4 자주 겪을 실패 패턴

| 증상 | 원인 | 대응 |
|---|---|---|
| `npm install xlsx` 시도 | zero-build 제약을 모름 | CLAUDE.md 규칙 2번을 프롬프트에 재인용 |
| `core/`에서 `document` 참조 | 편의상 DOM 접근 | 테스트가 즉시 실패하도록 Node 테스트를 먼저 붙여둘 것 |
| 유틸 함수 중복 생성 | 기존 모듈 미탐색 | "새 파일 만들기 전에 `src/core/util/` 를 먼저 확인해라" 문구 상시 포함 |
| 골든 파일을 마음대로 갱신 | 실패를 없애려는 최단 경로 | "골든 갱신은 금지. 불일치는 보고만 해라" 명시 |
| UI CSS 하드코딩 | 디자인 토큰 미인지 | blackrabbit-ui showcase 페이지를 참조 문서로 지정 |

마지막 두 개가 특히 중요합니다. 골든 파일 무단 갱신은 회귀를 조용히 통과시켜 버립니다.

## 7. 브랜치·커밋

기존 트렁크 기반 전략을 그대로 씁니다. 세션 단위가 곧 작업 단위이므로 별도 브랜치 규칙을 새로 만들 필요는 없습니다.

```
feat(parser): 타입 표기 파서 구현
test(parser): 타입 표기 케이스 24종 추가
chore(golden): C# 에미터 출력 형식 변경 반영
```

`chore(golden)` 접두사를 따로 두면 나중에 "출력 형식이 언제 바뀌었나"를 로그에서 바로 추적할 수 있습니다. 생성 코드를 쓰는 도구에서는 이 추적성이 꽤 값어치를 합니다.

## 8. 배포

GitHub Pages(`main` 브랜치 루트)로 서비스하고, 메인 사이트 목록에 항목을 추가합니다. blackrabbit-ui 갱신이 필요할 때만:

```bash
cd ~/work/blackrabbit-ui
npm run build
npm run sync -- sheet-exporter
```

벤더 파일은 대상 저장소에 함께 커밋됩니다. 디자인 시스템 업데이트가 앱을 예고 없이 깨뜨리지 않는다는 게 이 구조의 장점이니, 급하지 않으면 마일스톤 사이에만 동기화하세요.

## 9. S0 체크리스트

첫 세션을 시작하기 전에 사람이 직접 처리할 항목입니다.

- [ ] `npm run create` 로 스캐폴딩 생성
- [ ] SheetJS 배포본을 `vendor/sheetjs/` 에 배치 (LICENSE, VERSION 포함)
- [ ] 기획서를 `docs/spec.md` 로 복사
- [ ] `CLAUDE.md` 배치
- [ ] `package.json` 스크립트 확인: `test`, `fixtures`, `dev`
- [ ] `dependencies` 가 비어 있는지 확인
- [ ] 드림레시피 실제 시트 1장을 `test/fixtures/` 에 정의 파일로 옮겨두기

마지막 항목이 이 프로젝트의 나침반입니다. 가상의 시트로 만든 파서는 실제 시트를 만나면 대부분 깨지고, 그 시점에 구조를 다시 짜는 비용이 제일 큽니다.
